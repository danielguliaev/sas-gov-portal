# ТЗ: замечания к интерфейсу портала законов

**Проект:** `sas-gov-portal`  
**Статус документа:** накопительное ТЗ; работы по нему начаты после разрешения пользователя от 04.11.2026. У каждого требования отдельный статус.  
**Дата начала:** 04.11.2026.  
**Назначение:** накопительное ТЗ для последующих доработок пользовательского интерфейса законодательного портала. Новые замечания добавляются в этот документ; выполненные требования реализуются в рабочей ветке портала с проверками.

## UI-001. Блок «Прочие ресурсы» и отдельные сайты государственных органов

**Источник замечания:** сообщение пользователя со снимком навигационного блока портала от 04.11.2026.

### Текущее состояние

В боковой навигации портала законов отображаются переходы к следующим ресурсам:

1. Правительство штата
2. Судебная система
3. Законодательный орган
4. Город Лос-Сантос
5. Секретарь штата

### Требуемое состояние

Каждый из перечисленных ресурсов в будущем должен быть самостоятельным сайтом, а не отдельной страницей или разделом внутри законодательного портала.

На текущем этапе блок навигации рекомендуется обозначить заголовком **«Прочие ресурсы»**. До создания отдельных сайтов не следует предоставлять в этом блоке активные ссылки или маршруты к этим ресурсам. Заглушки, ведущие на страницы внутри портала законов, не должны восприниматься как отдельные государственные сайты.

Конкретные адреса сайтов, их дизайн, функционал и сроки реализации данным замечанием не определены; их следует согласовать отдельно перед разработкой.

### Критерии приёмки после разрешения на реализацию

- В навигации законодательного портала присутствует заголовок «Прочие ресурсы».
- Разделы «Правительство штата», «Судебная система», «Законодательный орган», «Город Лос-Сантос», «Секретарь штата» не открываются как внутренние страницы законодательного портала.
- Пока отдельные сайты не реализованы и их адреса не согласованы, в данном блоке нет активных ссылок на них.
- При создании отдельных сайтов интеграция ссылок рассматривается отдельным изменением.

**Приоритет:** не определён.  
**Состояние:** частично выполнено: в навигации библиотечного портала блок переименован в «Прочие ресурсы», ссылки убраны; самостоятельные сайты остаются отдельной будущей работой.

## UI-002. Создание вложенных структурных элементов кодекса

**Источник замечания:** сообщение пользователя от 04.11.2026.

### Текущее состояние

В интерфейсе законодательного портала пользователь не может создавать внутри кодекса подразделы, части и другие элементы иерархии. Наличие или отсутствие соответствующих серверных API не устраняет проблему: требуемое управление недоступно через пользовательский интерфейс.

### Требуемое состояние

Добавить в интерфейс управления кодексом возможность создавать структурные элементы различных типов (в частности, части и подразделы), выбирать их место в иерархии, создавать дочерние элементы внутри уже существующих и прикреплять статьи к нужному уровню структуры. Допустимые типы, глубина вложенности и правила нумерации должны определяться настройками соответствующего кодекса и требованиями основного ТЗ; конкретные ограничения не вводить без согласования.

Создание и изменение структуры должно быть доступно только пользователям с соответствующими правами. Для остальных пользователей иерархия должна отображаться в режиме чтения.

### Критерии приёмки после разрешения на реализацию

1. В интерфейсе редактирования кодекса есть доступное уполномоченному пользователю действие создания структурного элемента.
2. Можно указать тип элемента, его заголовок/номер и родительский элемент либо корень кодекса в соответствии с настройками иерархии.
3. Созданный элемент отображается в дереве кодекса на выбранном уровне и доступен для добавления вложенных элементов или статей, если это разрешено структурой.
4. После обновления страницы созданная иерархия сохраняется и правильно отображается читателям.
5. Неуполномоченный пользователь не может изменять структуру; ошибки валидации показываются понятным сообщением.

**Приоритет:** не определён.  
**Состояние:** основное создание реализовано: суперадминистратор может создавать новые типы уровней и вложенные узлы кодекса, редактировать названия и номера; расширенное администрирование и приёмка всех сценариев иерархии продолжаются.

## UI-003. Только три роли в законодательном портале

**Источник замечания:** третье замечание пользователя от 04.11.2026.

### Текущее состояние

Интерфейс портала законов предлагает больше трёх тестовых ролей, включая редактора библиотеки, издателя портала и законодателя. Для данного сайта такая ролевая модель не соответствует пожеланию пользователя.

### Требуемое состояние

В рамках **именно законодательного портала** должны существовать и быть представлены пользователям только три роли: **Суперадминистратор**, **Юрист**, **Читатель**.

В интерфейсе входа, профиля и управления доступом законодательного портала не должны отображаться дополнительные самостоятельные роли. Разграничение доступа к функциям портала следует привести в соответствие с этими тремя ролями. Конкретный перечень доступных действий для каждой роли необходимо определить с опорой на основное ТЗ и отдельно подтвердить при реализации.

Это требование относится к данному порталу и не устанавливает ролевую модель будущих самостоятельных сайтов других государственных органов (см. UI-001).

### Критерии приёмки после разрешения на реализацию

1. Законодательный портал предлагает пользователю ровно три роли с указанными наименованиями.
2. Дополнительные роли не отображаются как роли этого портала в меню входа, профиле и элементах администрирования.
3. Серверные проверки прав и интерфейсные ограничения согласованы для указанных трёх ролей; скрытие кнопок само по себе не считается достаточной защитой.
4. При изменении ролевой модели не теряется необходимая функциональность законодательной библиотеки — права на неё распределены между согласованными ролями.

**Приоритет:** не определён.  
**Состояние:** интерфейс реализован: видны только три роли; серверные роли внешних ведомственных процессов сохранены для будущего разнесения сайтов и интеграции IAM.

## UI-004. Центр уведомлений только законодательного портала

**Источник замечания:** четвёртое замечание пользователя от 04.11.2026.

### Текущее состояние

Границы центра уведомлений для законодательного портала не определены достаточно явно; система также включает или предполагает взаимодействие с другими государственными ресурсами.

### Требуемое состояние

**Центр уведомлений данного портала должен относиться только к законодательному порталу и его пользовательскому интерфейсу.** В нём показываются лишь события и сообщения, непосредственно связанные с работой пользователя внутри законодательной библиотеки.

Уведомления иных государственных сайтов, самостоятельных ведомственных систем и внешних ресурсов не должны автоматически попадать в этот центр. Каждый отдельный сайт из UI-001 в дальнейшем определяет собственную систему уведомлений независимо от законодательного портала.

Конкретные типы событий, для которых создаются уведомления внутри портала законов, следует определить при последующей детализации.

### Критерии приёмки после разрешения на реализацию

1. Центр уведомлений отображает только события законодательного портала.
2. Сообщения от посторонних сайтов и систем не попадают в список, счётчик непрочитанных и уведомительные индикаторы этого портала.
3. Уведомления доступны только надлежащему адресату с учётом трёх ролей из UI-003.
4. Интеграции с будущими отдельными сайтами не объединяют их уведомления с уведомлениями законодательного портала без отдельного требования.

**Приоритет:** не определён.  
**Состояние:** реализовано: интерфейс и API центра уведомлений работают только с событиями правовой библиотеки.

## UI-005. Переименование и очистка шапки и футера портала

**Источник замечания:** пятое замечание пользователя от 04.11.2026.

### Текущее состояние

В шапке портала используется круглый логотип с буквами «SA», наименование ресурса «Законодательная библиотека» и обозначение штата. В футере присутствуют слова «Демонстрационный портал» и ссылка на документацию API. Отдельная информационная плашка содержит текст: «Демонстрационная система ролевого мира. Примеры статей и документов не являются действующими правовыми нормами.»

### Требуемое состояние

**Официальное отображаемое название ресурса:** **«Правовая библиотека штата Сан Андреас»** (в точности в данной формулировке, без дефиса в «Сан Андреас»).

Из шапки убрать круглый логотип «SA»; пересмотреть подписи и наименования в шапке так, чтобы отображалось новое название ресурса.

В футере также использовать новое название ресурса; убрать словосочетание «Демонстрационный портал» и ссылку «Документация API». Остальные элементы футера, не затронутые замечанием, могут сохраняться.

Полностью убрать с пользовательской страницы информационную плашку со следующим текстом: «Демонстрационная система ролевого мира. Примеры статей и документов не являются действующими правовыми нормами.»

### Важное условие при будущей реализации

Удаление общей демонстрационной плашки само по себе не меняет юридический статус данных. Если в системе по-прежнему содержатся тестовые статьи и документы, их необходимо отличать от реально утверждённых правовых актов в соответствующих карточках и страницах документа, чтобы тестовые тексты не выдавались за действующее законодательство. Это условие не требует сохранять удаляемую общую плашку.

### Критерии приёмки после разрешения на реализацию

1. В шапке нет круглого логотипа с буквами «SA».
2. Шапка и футер содержат согласованное наименование «Правовая библиотека штата Сан Андреас».
3. Футер не содержит слов «Демонстрационный портал» и ссылки на документацию API.
4. Указанная общая плашка с предупреждением о демонстрационной системе полностью отсутствует в интерфейсе.
5. Тестовые юридические документы не обозначаются как официально действующие только вследствие изменения шапки или удаления общей плашки.

**Приоритет:** не определён.  
**Состояние:** реализовано: новый бренд, обновлённая шапка/футер, удалена общая плашка и ссылка на API-документацию.

## UI-006. Удаление всех демонстрационных маркировок из интерфейса

**Источник замечания:** шестое замечание пользователя от 04.11.2026.

### Требуемое состояние

В пользовательском интерфейсе **Правовой библиотеки штата Сан Андреас** убрать **все маркировки, обозначения и пояснения «демо» / «демонстрационный»**, а не только общую плашку, упомянутую в UI-005.

Требование охватывает главную страницу, каталог кодексов, карточки кодексов и статей, экран чтения, результаты поиска, последние редакции, уведомления и прочие пользовательские страницы. Удалить соответствующие бейджи, подписи, предупреждения и формулировки, связанные с демонстрационным статусом интерфейса или содержимого. Новые демонстрационные маркировки не добавлять.

Изменение касается **видимого интерфейса**; само по себе не требует удалять технические флаги, тестовые данные или инфраструктуру разработки. Оно уточняет и расширяет UI-005. При последующей реализации отдельно проверить, что фиктивные тексты не выдаются за официально утверждённые и действующие законы; до наполнения настоящими нормативными актами нельзя делать ложные заявления об их юридическом статусе.

### Критерии приёмки после разрешения на реализацию

1. Ни на одной пользовательской странице портала нет надписей «ДЕМО», «демо», «демонстрационный» и производных обозначений в роли маркировки тестового характера сайта или материалов.
2. В карточках и экранах чтения нет демонстрационных бейджей или предупреждающих блоков.
3. На главной странице, в поиске и в списке редакций нет демонстрационных пометок.
4. Удаление маркировок не приводит к автоматическому присвоению тестовым документам статуса официальных действующих нормативных актов.

**Приоритет:** не определён.  
**Состояние:** реализовано для маркировок пользовательского интерфейса: метки и предупреждающие блоки удалены; тестовые юридические данные и внутренние флаги остались в модели.

### Критерии приёмки после разрешения на реализацию

1. В нижней части страниц портала отображается «Copyright © 2026 State of San Andreas».
2. Старый текст копирайта заменён, дублирующих подписей нет.
3. Остальные требования к футеру из UI-005 также соблюдены.

**Приоритет:** не определён.  
**Состояние:** реализовано: в футере установлен дословный копирайт.

## UI-008. Корневые статьи непосредственно в дереве кодекса

**Источник замечания:** сообщение пользователя от 04.11.2026 с изображением бокового меню Penal Code.

### Требуемое состояние

В боковой панели кодекса **не отображать** отдельный служебный пункт «Статьи корня кодекса». Статьи, которые не принадлежат части, разделу, главе или другому структурному узлу, должны располагаться **непосредственно под названием кодекса**, на **одном уровне** с его частями и прочими корневыми структурными элементами.

Порядок определяется основным ТЗ: сначала структурные элементы текущего уровня, затем статьи этого уровня, отсортированные по юридическому номеру. Корневые статьи должны оставаться видимыми как непосредственные элементы кодекса и при открытом вложенном разделе; их постоянные ссылки должны вести на конкретные статьи. У вложенных разделов собственные статьи располагаются внутри соответствующих ветвей, а не в отдельном глобальном блоке «Статьи раздела» боковой панели.

### Критерии приёмки

1. Пункт «Статьи корня кодекса» полностью отсутствует в боковой панели.
2. Под названием кодекса находятся части, главы и другие корневые узлы, за ними — корневые статьи на том же уровне вложенности.
3. Корневая статья видна в структуре даже при просмотре другого раздела кодекса.
4. По ссылке на корневую статью открывается нужная карточка, не теряется постоянный ID.
5. Боковой индекс не выгружает полный юридический текст и поддерживает дозагрузку для больших кодексов.

**Состояние:** реализовано в пользовательском интерфейсе и API, добавлены автоматические и браузерные тесты.

## UI-009. Перепроектировать администрирование категорий и пользовательских полей

**Источник замечания:** сообщение пользователя от 04.11.2026 со скриншотом страницы /admin/categories.

### Проблема

Страница отображает все категории, их формы переименования, все поля, формы редактирования вариантов и создания новых полей одной длинной вертикальной лентой. Поиск нужной настройки затруднён; у всех действий одинаковый визуальный вес, а смысл взаимосвязанных форм неочевиден.

### Требуемое состояние

Сделать ориентированный на администратора, а не на структуру базы данных, интерфейс. Разделить **выбор категории** и **редактирование выбранной категории**: слева удобный список с поиском, счётчиками и контекстом кодекса, справа сведения выбранной категории и компактный список её полей. Настройки конкретного поля, значения справочника, переименование и добавление нового поля показывать по запросу пользователя, а не раскрывать одновременно на весь экран. Обеспечить ясные кнопки «Новая категория», «Добавить поле», «Сохранить», понятные подсказки для типов и правил после первого использования. Поддержать клавиатурную навигацию, состояния пустого списка, ошибок и сохранения, а также адаптивное отображение на небольших экранах.

Управление пользовательскими полями, режимом одиночного/множественного выбора, вариантами, включением вариантов и глобальными/кодексными категориями сохраняет ограничения основного ТЗ (REQ-038—REQ-044). Использованные типы полей и справочники не должны терять историю из-за дизайна.

### Критерии приёмки

1. При входе не отображается длинный список открытых редакторов всех категорий: одновременно редактируется одна выбранная категория.
2. Есть быстрый поиск по категориям и выбор контекста кодекса, доступно явное создание новой категории.
3. Поля видны компактным списком с типом и состоянием; редактор и значения справочника раскрываются по явному действию.
4. Правила неизменяемости уже использованных полей понятны до сохранения, сервер остаётся источником проверки прав и ограничений.
5. Сценарии создания категории, добавления и изменения поля, добавления, переименования и отключения варианта проверены в браузере.
6. Интерфейс читабелен и доступен на широких и узких экранах.

**Приоритет:** высокий.  
**Состояние:** реализовано: двухпанельный адаптивный интерфейс выбора категорий, поиск, адресуемый контекст и последовательное редактирование полей/справочников; ограничения проверяются сервером, сценарии создания и изменения выполнены в браузере.

## UI-010. Доступное создание нового кодекса

**Источник замечания:** сообщение пользователя от 04.11.2026 «До сих пор нет возможности создать новый кодекс».

### Требуемое состояние

Суперадминистратору должен быть очевиден путь **«Управление библиотекой → Кодексы → Создать кодекс»**. Прямой переход к созданию должен быть доступен из общего каталога кодексов. Форма должна содержать название, сокращение, юрисдикцию и понятный выбор первоначальных типов уровней (базовый шаблон либо настройка с чистого листа). При успешном создании открывается новый кодекс с возможностью добавить главы, части и статьи. Обязательные поля, уникальность имени в пределах юрисдикции и допустимый шаблон проверяются **на сервере**; пользователь получает объяснимое сообщение при конфликте. Создание кодекса и первичной иерархии должно быть атомарным.

### Критерии приёмки

1. Главная кнопка создания легко находится в каталоге и в административном разделе «Кодексы».
2. Только суперадминистратор может вызвать соответствующий API; обычный читатель и юрист не могут создать кодекс.
3. Пустое имя, повтор имени в юрисдикции, неизвестная юрисдикция и неверный шаблон дают понятную ошибку, не создавая пустого кодекса.
4. Успешно созданный кодекс появляется в общем каталоге, сохраняется между перезапусками и открывается по постоянной ссылке.
5. Выбранные начальные уровни созданы атомарно и могут быть настроены администратором позже; пустой шаблон не блокирует дальнейшее ручное создание уровней.
6. Проверен браузерный путь от кнопки «Создать кодекс» до чтения открытого кодекса.

**Приоритет:** высокий.  
**Состояние:** реализовано: кнопка создания в каталоге и администрировании, проверка прав и названия, атомарная стандартная или пустая иерархия, постоянная ссылка; дополнительно добавлены редактируемые реквизиты публикации кодекса по REQ-022.

## UI-011. Удобная панель настройки иерархии кодекса

**Основание:** замечание пользователя с изображением прежней страницы управления иерархией.

**Требование:** вместо длинной последовательности открытых форм предоставить отдельные сценарии «Уровни структуры», «Переместить раздел» и «Порядок разделов». Уровни выбираются из компактного списка; справа видны настройки только одного выбранного уровня. Допустимые родительские типы обозначаются ясными отметками. Добавление уровня доступно отдельной кнопкой, удаление типа находится среди опасных действий и требует проверки последствий и подтверждения. Перемещение выполняется только после предварительной проверки, ручная сортировка поддерживает кнопки и перетаскивание. Панель доступна с клавиатуры и адаптируется под узкие экраны.

**Критерии приёмки:** работают выбор уровня и редактирование допустимых родителей, создание типа, просмотр исключения типа и переносов, изменение порядка; тексты понятны без знания схемы БД; опасные действия нельзя выполнить одним случайным нажатием; проверены браузером.

**Статус:** реализована новая рабочая панель, приёмочное тестирование выполняется.

## UI-012. Удобная панель настройки юридических связей

**Основание:** замечание пользователя с изображением прежней страницы настройки юридических связей.

**Статус:** реализована новая рабочая панель, приёмочное тестирование выполняется.

## L10N-003. Русские названия классов правонарушений

В пользовательском интерфейсе во всех списках, карточках, фильтрах и формах вместо внутренних кодов или английских названий показывать «Тяжкое преступление» (felony), «Проступок» (misdemeanor), «Нарушение» (infraction). Внешние ID, хранилище и контракты API остаются неизменными. Употребление пользователем слова Fraction трактуется как Infraction; не создавать четвёртый вид.

**Критерий приёмки:** все три значения правильно отображаются при редактировании, чтении и поиске, сохраняются с прежними ключами.

**Статус:** отображаемые значения заменены, регрессионные проверки выполняются.
